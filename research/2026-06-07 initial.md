# OpenTogetherTube → follow-only mpv client: protocol research

**Goal:** a native player (mpv) that *joins an OTT room as a passive viewer* — it follows
room playback (source, play/pause, seek, speed) and **never issues commands**. This document
is the protocol reference for building that mpv plugin later.

**Source of truth:** `dyc3/opentogethertube`, pinned to commit
`b6122ca45c975a7b105cfbcfc84d7c0ed17dd09b` (2026-06-02). All claims below are cited to
file+line at that commit (see [Sources](#sources)). Line numbers are exact for this commit;
re-verify if you bump versions, because `RoomRequestType` is positional (not relevant for a
pure follower, but noted).

All frames are JSON text, discriminated by a top-level `action` string.

---

## TL;DR for the plugin author

1. `GET /api/auth/grant` → `{ "token": "..." }`. Mint once, reuse.
2. Open WS to `ws[s]://<host>[<base_url>]/api/room/<roomName>`.
3. Send exactly one frame: `{"action":"auth","token":"<token>"}`. **Send nothing else, ever.**
4. Server replies with a **full `sync`** snapshot, then a `you` frame. Use the full sync to
   load the file and jump to position.
5. Thereafter you receive `sync` frames **only when room state changes** (play/pause/seek/
   source/speed) — there is **no periodic position heartbeat**. Each such frame is a *delta*
   carrying only the changed fields, with `playbackPosition` (when present) being the live
   head position at send time.
6. Between frames, let mpv's own clock run. At ±10 s tolerance you only need to react to
   events; continuous drift correction is unnecessary.
7. A follower that never sends `status` does **not** stall anyone — `playerStatus` is purely
   informational server-side.

## 1. Connection lifecycle

### 1.1 WebSocket endpoint
`ws://` or `wss://` mirroring page protocol, host, optional configured `base_url`, then
`/api/room/<roomName>`:

```
wss://<host>/api/room/<roomName>
```

The browser also appends `?reconnect=true` on reconnects; not required for a fresh connect.
[connection.ts L86–L92, L116]

### 1.2 Auth token
`GET /api/auth/grant`. If you pass a valid `Authorization: Bearer <token>` it echoes it back;
otherwise it mints a new token. Response body: `{ "token": "<token>" }` (also sets an
httpOnly `token` cookie, which a non-browser client can ignore in favor of the body).
[auth/index.ts L99, L122]

### 1.3 Handshake
Immediately after the socket opens, the client sends:

```json
{ "action": "auth", "token": "<token>" }
```

This is the browser's first and only mandatory send. [connection.ts L155–L158]

### 1.4 What you receive on join
After auth the server, in order:
1. sends a **full sync**: `Object.assign({action:"sync"}, room.syncableState())` — i.e. every
   syncable prop, with `playbackPosition` set to the live head (see §3.2);
2. sends `{ "action":"you", "info": { "id": <clientId> } }` (your client id);
3. processes your join internally.

[clientmanager.ts L138–L143 (full sync), L175 (`you`)]

So the **full sync is your bootstrap**: read `currentSource`, `isPlaying`,
`playbackPosition`, `playbackSpeed` from it and initialize mpv.

## 2. Server → client message catalog

`ServerMessage` union, discriminated by `action`:
`sync`, `unload`, `chat`, `event`, `eventcustom`, `announcement`, `user`, `you`.
[messages.ts, `ServerMessage`]

For a follower, only **`sync`** drives playback. Useful secondary ones:

| action      | meaning for a follower |
|-------------|------------------------|
| `sync`      | playback state (the one that matters). |
| `unload`    | room torn down → disconnect, do not reconnect. |
| `you`       | your client id (informational). |
| `chat`, `event`, `eventcustom`, `announcement`, `user` | ignorable for playback. |

(`unload` is documented as a control signal to the client manager rather than a literal wire
frame, but treat any `unload` you see as "stop and disconnect".) [messages.ts, `ServerMessageUnload`]

## 3. The `sync` message

### 3.1 Shape (all fields optional — it is a delta)
`ServerMessageSync` fields relevant to playback (others omitted):

```ts
action: "sync"
isPlaying?: boolean
playbackPosition?: number      // seconds
playbackSpeed?: number
currentSource?: QueueItem | null
// also may carry: queue, name, title, visibility, queueMode, grants, voteCounts, … (ignore)
```
[messages.ts, `ServerMessageSync`]

`currentSource` is a `QueueItem` (`= Video & QueueItemExtras`), so it may include
`src_url`, `hls_url`, `dash_url`, `subtitleUrl`, `mime`, `length`, `startAt`, `endAt`.
[video.ts, `VideoMetadata` / `QueueItem`]

### 3.2 Position semantics — **read this twice**

`playbackPosition` is **not** a stored snapshot + timestamp. Every outbound sync overwrites it
with `realPlaybackPosition`, the server's *interpolated live head* at the instant the message
is built:

```
syncableState(): sync.playbackPosition = this.realPlaybackPosition          // room.ts L841
realPlaybackPosition = isPlaying ? playbackPosition + (now − _playbackStart)*speed
                                 : playbackPosition                          // room.ts L721–L726
```
[room.ts L713–L726, L839–L841]

Implication: the number you receive is "where the head is *now*". There is no timestamp to
correct against; subtract your own receive latency if you want, but at ±10 s it's noise.

### 3.3 Cadence — **event-driven, no heartbeat**

The room loop runs `update()` then `sync()` every **1 s**, but `sync()` is a **no-op unless
some prop is dirty**, and steady playback marks nothing dirty (`update()` advances nothing —
position is derived, not stored). So during normal playback **no sync frames are sent at all**.
[roommanager.ts L51, L81–L82; room.ts L860–L863; room.ts L737–L825 (update body marks no
playback props dirty in steady state)]

`sync()` builds the delta as `_.pick(syncableState, dirtyProps)` and debounces 50 ms.
[room.ts L828 (`throttledSync` debounce 50 ms), L860–L884 (delta = picked dirty props)]

You therefore receive a position-bearing sync **only on real events**. Verified field sets:

| Event              | Delta you receive                                  | Notes |
|--------------------|----------------------------------------------------|-------|
| Join               | **full** state incl. live `playbackPosition`       | bootstrap (§1.4) |
| Pause              | `{ isPlaying:false, playbackPosition:<frozen> }`    | `pause()` flushes head into `playbackPosition` (dirty) then clears playing |
| Resume/play        | `{ isPlaying:true }` **(no position)**              | resume from your local head |
| Seek               | `{ playbackPosition:<new> }`                        | `isPlaying` unchanged |
| Speed change       | `{ playbackSpeed:<x> }`                             | |
| Source change/next | `{ currentSource, playbackPosition, isPlaying, … }` | new file + reset head |

[pause/play: room.ts L1125–L1144; flush marks position dirty: room.ts L973–L979; delta pick: room.ts L876]

Because resume carries no position, the follower must keep its own head while paused so it can
continue from the right spot. (At pause the server stored the exact head, and your mpv was
paused at the same spot, so they agree.)

## 4. Resolving the media URL

The browser's `OmniPlayer` picks, for a direct file:

```
url = currentSource.src_url ?? currentSource.id
```
[OmniPlayer.vue L111]

For `service: "direct"`, the `id` **is** the media URL (the direct info-extractor uses
`"direct"` as its service id and the URL as the id). So:

```
mpv_url = currentSource.src_url || currentSource.id
```

covers your self-hosted MP4 case. (`hls_url`/`dash_url` exist for HLS/DASH sources if you ever
serve those; same `?? id` fallback pattern.) [direct.ts L47–L48; OmniPlayer.vue L76, L91, L111]

Subtitles, if set, arrive as `currentSource.subtitleUrl` — mpv can sub-add it. [video.ts `VideoMetadata.subtitleUrl`]

## 5. What the follower sends: nothing (and why that's safe)

For a pure follower, the only frame you ever send is the `auth` handshake (§1.3).

`status` (`ClientMessagePlayerStatus`) is optional. The server stores the reported
`playerStatus` on the user record and only **rebroadcasts it to other clients** as part of user
info — it is **never read to gate, pause, or block playback**. A follower that never reports
status simply shows as `none` to others and affects no one. [clientmanager.ts L188–L196
(status → UpdateUser); room.ts L491 (only echoed in user info); PlayerStatus enum:
types.ts L35–L40; no playback gating uses `playerStatus`]

> Design note: this is the key reason "follow-only and silent" is viable in OTT specifically.
> Some sync systems gate `play` on all clients reporting "ready"; OTT does not.

Do **not** send `req`/`status`/`notify`/`kickme`. (`req` with a `RoomRequest` is how the
browser controls the room — out of scope for a follower. For reference, control would be
`{"action":"req","request":{"type":<RoomRequestType>,…}}` with `RoomRequestType` a *numeric*
enum: Playback=2 `{state}`, Seek=4 `{value}`, PlaybackSpeed=16 `{speed}`. Listed only to be
explicit about what we are deliberately NOT doing.) [messages.ts `ClientMessage`,
`RoomRequest`, `RoomRequestType`]

## 6. Reference follower algorithm (±10 s tolerance)

Player-agnostic; map the verbs onto mpv (`loadfile`, `set pause`, `set speed`,
`seek <abs> absolute`, observe `time-pos`).

```
state: { src_url, playing, speed }   // local mirror

on GET /api/auth/grant -> token
open WS; send {action:"auth", token}

on frame:
  if action == "unload": disconnect(no-reconnect); stop
  if action != "sync": ignore
  delta = frame

  # 1. source
  if "currentSource" in delta:
      if delta.currentSource is null:
          mpv.stop(); state.src_url = null
      else:
          url = delta.currentSource.src_url or delta.currentSource.id
          if url != state.src_url:
              mpv.loadfile(url)
              if delta.currentSource.subtitleUrl: mpv.sub_add(...)
              state.src_url = url
              need_seek = true     # force position apply after load

  # 2. speed
  if "playbackSpeed" in delta:
      state.speed = delta.playbackSpeed
      mpv.set_speed(state.speed)

  # 3. play/pause
  if "isPlaying" in delta:
      state.playing = delta.isPlaying
      mpv.set_pause(not state.playing)

  # 4. position (authoritative when present)
  if "playbackPosition" in delta:
      target = delta.playbackPosition
      # tiny forward bias for in-flight latency while playing (optional, <1s)
      if state.playing: target += est_latency
      if need_seek or abs(mpv.time_pos - target) > SEEK_THRESHOLD:   # e.g. 3s
          mpv.seek_absolute(target)
      need_seek = false
```

Notes:
- **No background reconciliation loop needed** at ±10 s. mpv's clock vs. server wall-clock drift
  over a single video is far under 10 s, and every meaningful divergence (seek/pause/source) is
  pushed as an event you already handle.
- **Buffering on load:** after `loadfile`, mpv takes time to become ready; the `playbackPosition`
  in that frame was "now" at send. For ±10 s, applying it directly (optionally `+ small const`)
  is fine. A tighter build would re-derive `target = pos + (ready_time − recv_time)`.
- **Resume has no position** (§3.3) — do not seek on a bare `{isPlaying:true}`; just unpause.
- Reconnect: on socket drop, reconnect and you'll get a fresh **full sync** to re-bootstrap.

## 7. Open questions / to verify when building the plugin

1. **WS subprotocol / headers:** the browser opens a plain `new WebSocket(url)` with no
   subprotocol and authenticates in-band via the `auth` frame; confirm no reverse proxy in
   *your* deployment requires `Origin`/cookie. (Auth is in-band, so cookie shouldn't be needed.)
   [connection.ts L116, L155–L158]
2. **Private/locked rooms:** confirm whether room grants/visibility reject an anonymous minted
   token for the rooms you use; if so the token may need to be associated with a logged-in
   session. Not exercised here.
3. **`currentSource.src_url` presence for `direct`:** confirmed the player falls back to `id`,
   and for `direct` the `id` is the URL — but verify on *your* instance that the URL in `id` is
   reachable from the follower's network (it's your own server, so likely yes).
4. **Exact field set per event** is verified above against `main`; if you pin a different OTT
   version, re-check §3.3 (the dirty-prop mechanism is stable, the specific handlers could shift).
5. **HLS/DASH sources:** out of scope (you stated MP4 direct), but `hls_url`/`dash_url` exist if
   that ever changes.
